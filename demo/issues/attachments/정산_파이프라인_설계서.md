# 정산 파이프라인 재작성 설계서

- **이슈:** #63
- **선행:** #61(통합 함수), #62(순서 버그)
- **작성:** 결제정산팀
- **상태:** 승인

## 1. 배경 / 문제
적용 순서 버그(#62)가 반복되는 근본 원인은, 정산 합산이 한 함수에 절차적으로 뭉쳐 있어
**단계별 검증·표시·재사용이 불가능**하다는 점이다. 단계를 1급 객체로 분해한다.

## 2. 설계 목표
- 각 정산 단계를 `(단계명, 금액)` 으로 명시적으로 산출한다.
- 합산 로직과 단계 정의를 분리한다.
- 영수증/정산서가 단계별 내역을 그대로 쓸 수 있게 한다.

## 3. 단계 정의 (`_steps` 제너레이터)
순서와 부호는 아래를 따른다. (부가세 과세 기준은 정책서 2항 = 할인 전 공급가 유지)

| 순서 | 단계명 | 금액 | 비고 |
|---|---|---|---|
| 1 | 공급가 | `final_charge(order)` | 수수료 포함 |
| 2 | 부가세 | `vat(공급가)` | **할인 전 기준** |
| 3 | 쿠폰할인 | `apply_coupon(공급가, rate) - 공급가` | 음수(차감) |

## 4. 공개 API
- `settlement_total(order, coupon_rate=0.0) -> int` : 단계 합산만 위임
- `settlement_breakdown(order, coupon_rate=0.0) -> dict[str, int]` : 단계별 내역(영수증용)

## 5. 불변식 / 검증
- `settlement_total == sum(breakdown.values())`
- 과세 기준은 #60/#62 결론(할인 전 공급가) 유지
- 쿠폰 0% → 쿠폰할인 단계 = 0

## 6. 비범위
- 정액 쿠폰, 다중 쿠폰 중첩은 본 설계 범위 밖(후속).
